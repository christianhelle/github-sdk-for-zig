# Usage guide

This guide covers the GitHub REST API client in this package. The client is generated by [openapi2zig](https://github.com/christianhelle/openapi2zig) from GitHub's REST API description, so its shape follows that description. For a production-grade, full-featured reference, see [chlogr](https://github.com/christianhelle/chlogr), a changelog generator built on this package.

## Install

Requires Zig 0.17.1 or later.

```bash
zig fetch --save git+https://github.com/christianhelle/github-sdk-for-zig#v0.1.0
```

Add the module in `build.zig`:

```zig
const github = b.dependency("github", .{
    .target = target,
    .optimize = optimize,
});
exe.root_module.addImport("github", github.module("github"));
```

The package exposes:

| Declaration | Contents |
| --- | --- |
| `github.init` | Creates a client for api.github.com |
| `github.client` | Every operation, plus `Client` and the request helpers |
| `github.models` | A struct for every schema |
| `github.runtime` | `Owned`, `ApiResult`, `RawResponse` and `HttpObserver` |

## Create a client

```zig
var client = github.init(allocator, io, token);
defer client.deinit();
```

The client borrows `token` and the base URL, so they must outlive it. In a `main(init: std.process.Init)`, use `init.gpa` for the allocator and `init.io` for `io`.

### Authentication

Every generated operation sends a non-empty token as `Authorization: Bearer <token>`. Any token GitHub accepts works, such as a fine-grained or classic personal access token, a GitHub App installation token, or `GITHUB_TOKEN` in Actions.

An empty string sends anonymous requests, which GitHub limits to 60 per hour.

### GitHub Enterprise Server

Use `Client.init` and set the base URL yourself, without a trailing slash:

```zig
var client = github.Client.init(allocator, io, token);
defer client.deinit();
client.withBaseUrl("https://github.example.com/api/v3");
```

`Client.init` leaves the base URL empty and doesn't read it from the OpenAPI description, so requests fail until you call `withBaseUrl`. `github.init` does this for you.

### Default headers

`default_headers` are added to every request. This pins the [API version](https://docs.github.com/rest/about-the-rest-api/api-versions):

```zig
client.default_headers = &.{.{ .name = "X-GitHub-Api-Version", .value = "2026-03-10" }};
```

## Find an operation

Function names come from the GitHub operation ID, so `issues/list-for-repo` becomes `issuesListForRepo`. Find an operation ID on the matching page of the [REST API docs](https://docs.github.com/rest), or search `src/client.zig`, where each operation has its summary and description in a comment.

Path and query parameters are positional, in the order of the function signature. Pass `null` for optional query parameters you don't want to send:

```zig
var issues = try github.client.issuesListForRepoRaw(
    &client,
    "christianhelle",
    "chlogr",
    null, // milestone
    "closed", // state
    null, // assignee
    null, // type
    null, // creator
    null, // mentioned
    null, // issue_field_values
    null, // labels
    "updated", // sort
    "desc", // direction
    null, // since
    100, // per_page
    1, // page
);
defer issues.deinit();
```

The [search_repositories](../examples/search_repositories.zig) example does the same with a search query.

The same operations are also grouped by path under `github.client.resources`, with lowercased names. For example, `github.client.resources.repos.reposget` calls `reposGet`.

## Choose a call form

Most operations come in three forms. Choose by how much of the response you need.

| Form | Example | Returns | Use it when |
| --- | --- | --- | --- |
| Plain | `reposGet` | `Owned(T)` | Any failure can be treated the same way |
| Result | `reposGetResult` | `ApiResult(T)` | You need to react to the status or error body |
| Raw | `reposGetRaw` | `RawResponse` | You want to decode the body yourself |

Operations that have no response body, such as `reposDelete`, return `!void` in their plain form.

### Plain

```zig
var repository = try github.client.reposGet(&client, "christianhelle", "chlogr");
defer repository.deinit();

std.debug.print("{s}\n", .{repository.value().full_name});
```

A non-2xx status is reported as `error.ResponseError`, and a body that doesn't match the model as `error.ResponseParseError`. The status and body are discarded, so use the Result form if you need them.

### Result

```zig
var result = try github.client.reposGetResult(&client, owner, repo_name);
defer result.deinit();

switch (result) {
    .ok => |*repository| std.debug.print("found {s}\n", .{repository.value().full_name}),
    .api_error => |response| std.debug.print("GitHub answered {d}: {s}\n", .{
        @intFromEnum(response.status),
        response.body,
    }),
    .parse_error => |failure| std.debug.print("{s} while parsing: {s}\n", .{
        failure.error_name,
        failure.raw.body,
    }),
}
```

Transport failures, such as a failed connection, are still returned as Zig errors by the `try`.

### Raw

```zig
var raw = try github.client.reposGetRaw(&client, "christianhelle", "chlogr");
defer raw.deinit();

if (raw.status != .ok) return error.GitHubApiError;
```

The Raw form never turns a status into an error, which makes it the right choice when a status is the answer. For example, `pullsCheckIfMergedRaw` answers 204 for merged and 404 for not merged, as the [check_merged](../examples/check_merged.zig) example shows.

## Memory ownership

The client allocates with the allocator you gave it, and each response owns its memory:

- Declare responses with `var` and call `deinit`, because `deinit` and `value()` need a mutable pointer.
- `deinit` frees everything reached through `value()`, including strings. Copy anything that needs to live longer.
- `parseRawResponse` takes ownership of the `RawResponse` you pass it. Call `deinit` on the result, not on the raw response.

## Untyped responses and your own structs

Of the 1,224 generated operations, 495 return a typed model and 334 return nothing. The other 395 return untyped JSON, including most list operations. `reposListReleases`, `issuesListForRepo` and `pullsList`, for example, return `Owned([]const std.json.Value)`.

For those, call the Raw form and decode into a struct that declares only the fields you need. The same approach works when a typed model is more than you want, and it's how [chlogr's client](https://github.com/christianhelle/chlogr/blob/main/src/github_api.zig) decodes releases, pull requests and issues:

```zig
const Release = struct {
    tag_name: []const u8,
    published_at: ?[]const u8 = null,
    draft: bool = false,
};

var raw = try github.client.reposListReleasesRaw(&client, owner, repo_name, 100, 1);
defer raw.deinit();

const parsed = try std.json.parseFromSlice([]const Release, allocator, raw.body, .{
    .ignore_unknown_fields = true,
});
defer parsed.deinit();
```

Typed models come straight from the OpenAPI description. If GitHub omits a field that the description marks as required, the typed call fails with a parse error, and decoding into your own struct gets around it.

Model names follow the schema names, so many need quoting: `github.models.@"full-repository"`.

## Pagination

Response headers aren't exposed, so you can't follow the `Link` header. Request pages by number and stop at the first page with fewer items than you asked for. GitHub allows up to 100 items per page on most endpoints.

```zig
const page_size = 100;

var page: i64 = 1;
while (true) : (page += 1) {
    var raw = try github.client.reposListReleasesRaw(&client, owner, repo_name, page_size, page);
    defer raw.deinit();

    if (raw.status.class() != .success) return error.GitHubApiError;

    const parsed = try std.json.parseFromSlice([]const Release, allocator, raw.body, .{
        .ignore_unknown_fields = true,
    });
    defer parsed.deinit();

    for (parsed.value) |release| std.debug.print("{s}\n", .{release.tag_name});

    if (parsed.value.len < page_size) break;
}
```

If you filter results, as [chlogr](https://github.com/christianhelle/chlogr/blob/main/src/github_api.zig) does with draft releases, compare the unfiltered count. Otherwise a page that filters down to a few items looks like the last one. A few endpoints paginate differently, so check the REST API docs for the endpoint you're calling. The full program is in [examples/list_releases.zig](../examples/list_releases.zig).

## Request bodies

Operations that send a body take it as a `std.json.Value`, so build it with an `ObjectMap`. An arena is the simplest way to manage it:

```zig
var body: std.json.ObjectMap = .empty;
try body.put(arena, "title", .{ .string = "Found a bug" });
try body.put(arena, "body", .{ .string = "Details here" });

var result = try github.client.issuesCreateResult(&client, owner, repo_name, .{ .object = body });
defer result.deinit();
```

Check the REST API docs for the fields each operation accepts. The body isn't checked against the schema before it's sent, so a mistake comes back from GitHub as an `api_error`, usually with status 422. The full program is in [examples/create_issue.zig](../examples/create_issue.zig).

## Requests by path

Use `requestRawWithExtraHeaders` for an endpoint the generated client gets wrong or doesn't have. These helpers **don't send your token**, so add the header yourself:

```zig
const authorization = [_]std.http.Header{.{
    .name = "Authorization",
    .value = try std.fmt.allocPrint(arena, "Bearer {s}", .{token}),
}};
const url = try std.fmt.allocPrint(arena, "{s}/rate_limit", .{client.base_url});

var raw = try github.client.requestRawWithExtraHeaders(&client, .GET, url, null, &authorization);
defer raw.deinit();
```

The URL is used as you give it, so percent-encode any values you put in it. `getRaw` and `postJsonRaw` are shorter, but they can only send a token through `default_headers`. The full program is in [examples/raw_request.zig](../examples/raw_request.zig).

## Rate limits and errors

GitHub reports rate limiting with a 403 or 429 status, which you can see in the Result and Raw forms. Because response headers aren't exposed, `Retry-After` and `X-RateLimit-*` aren't available. Call `rateLimitGet` to check your remaining quota instead, as the [rate_limit](../examples/rate_limit.zig) example does.

The client doesn't retry requests or apply timeouts. Add retries in your own code if you need them, following GitHub's [best practices](https://docs.github.com/rest/using-the-rest-api/best-practices-for-using-the-rest-api).

Requests without a body follow up to 3 redirects, and your token is only sent to the original origin. Requests with a body don't follow redirects, so you get the 3xx response.

## Threads

Don't share a `Client` between threads. Create one per thread, each with its own `deinit`:

```zig
var worker = github.init(allocator, io, token);
defer worker.deinit();
```

The [parallel_requests](../examples/parallel_requests.zig) example fetches several repositories this way. [chlogr](https://github.com/christianhelle/chlogr/blob/main/src/github_api.zig) fetches pages on worker threads, giving each its own client.

## Observing requests

`http_observer` is called around every request, which is useful for logging and metrics. Any callback can be `null`:

```zig
const Logger = struct {
    fn onResponse(
        _: ?*anyopaque,
        method: std.http.Method,
        url: []const u8,
        status: std.http.Status,
        _: []const std.http.Header,
        _: []const u8,
        duration_ns: u64,
    ) void {
        std.debug.print("{t} {s}: {d} in {d} ms\n", .{
            method,
            url,
            @intFromEnum(status),
            duration_ns / std.time.ns_per_ms,
        });
    }
};

client.http_observer = .{
    .ctx = null,
    .onRequest = null,
    .onResponse = &Logger.onResponse,
    .onError = null,
};
```

`onRequest` receives the request headers, including `Authorization`, so don't log them as they are. `onResponse` currently receives an empty header list.

The [observe_requests](../examples/observe_requests.zig) example counts requests and failures through `ctx`.

## Compile times

`src/client.zig` is about 3.8 MB, but Zig only compiles what you call. A first Debug build of a small program using one operation took about 15 seconds on a Windows desktop, and rebuilds use the cache.

## Known limitations

### Generator leftovers

- `Client.organization` and `Client.project` send `OpenAI-Organization` and `OpenAI-Project` headers if set. They have no meaning for GitHub, so leave them unset.
- `github.runtime` includes server-sent event helpers and a `CancellationToken`, and `Client` has a `cancel_check` field. No GitHub operation streams, so you won't need them.
- Some `GET` operations, such as `reposGetContent`, take a `requestBody` because of how the description is written. Pass `.null`.

### Other limits

- Response headers aren't available, which limits pagination and rate limit handling as described above.
- Request bodies and many responses are untyped, as described in [Untyped responses](#untyped-responses-and-your-own-structs).
- `src/compile_check.zig` proves that operations compile, not that each one works against GitHub. Only the operations used by the examples have been run against the live API, and `create_issue` hasn't been run because it writes to GitHub.
